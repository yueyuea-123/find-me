# AI 开发规则（project_rules）

> **文档定位**：约束后续 AI 执行 `tasks.md` 任务时的行为，不包含具体实现细节（保持跨任务可复用）；不与 `proposal.md` / `design.md` / `tasks.md` 冲突。
> **上位依据**：`proposal.md`（做什么，V1.2 单一事实源）、`design.md`（怎么做）、`tasks.md`（先做什么，T1～T19）。
> **性质**：回溯补建项目的执行纪律；重点是防止"文档说已实现、代码实际没有"与"顺手改出范围外功能"两类返工。

---

## 1. 任务范围控制
- 一次只执行 `tasks.md` 中编号明确的**单个任务**（如 T8），不做任务编号外的"顺手优化"。
- 发现新问题或缺失能力：记录到 `tasks.md` 或 `change-log.md`，不直接修改；需新增范围的走变更流程（见 §3）。
- 所有功能以 `proposal.md` 为准，不擅自扩展；P1/P2 与"明确不做的事"（proposal §5.2/§5.3/§10）不在执行范围内。
- **状态纪律**：T7～T10 代码层已落地（2026-11-19，标注「已实现(代码层)」），但相关 AC（AC-02～AC-06、AC-16/17）在**真机验证通过前**，不得在任何文档、汇报或验收单中标记为通过。代码层完成 ≠ 真机验收通过。

## 2. 完成标准与验收
- 每个任务完成后，对照该任务在 `tasks.md` 的"完成标准"逐项自检，并执行其"验证方式"。
- 汇报固定四项：修改了哪些文件 / 如何验证 / 验证结果 / 剩余风险。
- 汇报后停止，等待人工确认；未通过验收不得进入下一任务、不得与其他任务合并提交。
- 双基准（决策 D10）：功能正确性以**需求基线**（proposal §11 AC + MVP 冻结清单）为准；工程质量以 **qa 门禁**为准（静态 ≥90 且 0 P0 阻断、冒烟全过）。两者须同时满足，缺一不可。

## 3. 异常与依赖处理
- 文档缺失、依赖未满足、需求不清晰时，**停止并提问**，不自行猜测或引入未确认依赖。
- 新需求或方向变更：先产出变更提案 + 登记 `change-log.md`，经用户批准后再更新 proposal/design/tasks；提案未批准前不修改基线文档、不改代码（CR-001 的执行顺序为范例）。
- 任务前置依赖未闭合（如 T8 依赖 T7 的字段）时，不得跳级执行。

## 4. 语言、框架与包管理
- 前端：微信原生小程序（WXML / WXSS / JS），无第三方 UI 框架。
- 后端：云开发 CloudBase，NoSQL 文档数据库 + 云函数（Node.js）。
- 包管理：云函数各目录自带 `package.json`，沿用现有依赖；新增依赖必须先说明必要性并经用户确认。
- 环境：CloudBase `kkkyuer-d4g5w54lpb6ac6517`（与工程 AppID 匹配）；不得在代码中硬编码密钥或管理员 openid（用环境变量 `ADMIN_OPENIDS`）。

## 5. 目录结构与模块隔离
- 遵守 `design.md` §11 目录结构：`docs/`（规范与治理）、`miniprogram/pages`（21 注册页）、`miniprogram/utils`（6 模块）、`cloudfunctions`（6 有效云函数）、`qa`（门禁脚本）。
- 文档放 `iteam/docs/`（决策 D1），产品定义存量文档在 `document/`；不在两个目录重复维护同一事实源。
- 前端一律经云函数访问数据库，不直连集合；页面只做展示与交互，业务规则集中在 `store.js`。
- 残留目录 `example/`、`verify3d/`、`quickstartFunctions/` 在清理前不得被新代码引用（决策 D4：先核实引用再删）。

## 6. 命名与代码风格
- 业务 id 用 `xxx_时间戳_随机`，与云 `_id` 分离；每个业务集合含 `openid` + `createdAt` + `updatedAt`。
- 三维坐标统一 Y-up、单位米；家具变换字段为 `position/rotation/size`。
- 绑定主通道为 `nodes.furnitureId` + `items.currentNodeId`；`furniture.bindings` 仅作直接绑定补充，避免双绑定源（design §5）。
- 沿用现有文件命名与代码风格；格式化/Lint 以现有工程为准，不引入新的格式化工具链。

## 7. 安全与隐私红线
- 集合权限 PRIVATE，客户端直连拒绝；OPENID 从 `cloud.getWXContext()` 获取，忽略客户端传入。
- 家庭照片私有存储（`photos/{openid}/{roomId}/{photoId}`），后台不返回照片内容；错误上报脱敏，不发照片或物品明细。
- V1.2 主路径无第三方 AI 依赖；未经授权不得将用户数据用于第三方训练。
- 测试与演示不得使用真实家庭数据；密钥、管理员身份不写入代码或文档。

## 8. 文档同步
- 实现与文档不一致时，**先更新文档并说明差异，再继续实现**；不允许为迁就文档而虚构未落地能力（如声称模型变换/绑定已实现）。
- 每次变更同步更新 `change-log.md`（变更登记 + 执行进度）；CR-001 提案的执行清单逐项勾选，不出现"决策栏已批准、清单仍待批准"的自相矛盾。
- 口径统一：页面数 21（18 为陈旧）；photos/task 页为"可选降级、代码中仍注册"，不写"删除页面"；追溯矩阵属阶段 G、重验属阶段 G/H、回写提交属阶段 H。

## 9. Git 提交规则
- 主干开发 + 阶段 tag（决策 D9）；基线 tag `baseline/pre-sdd` 已打。每任务验收通过后**单独提交**，只提交本任务相关文件。
- 提交信息格式：`feat: complete T<编号> <任务名>`；阶段 tag 在该阶段所有任务验收后打。
- 提交前确认 `.gitignore` 生效（`node_modules/`、`*.log`）；`docs/` 治理文件与代码分 task 提交，不混杂。
- 当前 `docs/` 新增文件尚未提交：在阶段 F/G 文档定稿并经用户确认后，按阶段统一提交，不擅自提前 commit。

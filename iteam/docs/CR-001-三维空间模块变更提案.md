## 1. 变更原因与目标

**原因**：通过照片直接建立个人空间难度高（尺度不确定、建模质量与成本不可控），MVP 阶段以照片为主路径风险过大。

**目标**：改为提供一个**可自由编辑的三维场景**——用户手动创建房间布局、添加/移动/旋转/缩放三维模型，并将每个模型与物品信息及存放位置绑定，用于记录、查看和管理物品在空间中的位置。三维从"照片生成的产物"转变为"用户直接编辑的画布"。

**不变的核心原则**（继承产品总纲 V1.0）：物品管理优先于三维视觉效果；事实与预测分离（本方案无 AI 生成，场景结构与绑定均为用户确认事实）；失败可降级（列表通路常驻）；三维对象与逻辑位置解耦；数据可追溯。

## 2. 需求结构化

### 2.1 功能范围

| 编号 | 功能项 | 做什么 | 不做什么（边界） | 验收时看到什么 |
| --- | --- | --- | --- | --- |
| F-01 | 房间布局创建 | 手动设定房间名称、宽/深/高，生成可编辑地面与墙面 | 不做照片输入、不做 AI 自动重建、不承诺测量级精度 | 无模型时房间仍可创建并打开 |
| F-02 | 场景自由编辑 | 从模型库添加家具；对模型做移动/旋转/缩放（Y-up、单位米） | 不做模型自动识别、不做从零建模、不做照片级渲染 | 模型位置/角度/尺寸保存后重进一致 |
| F-03 | 模型—物品绑定 | 将模型与物品档案及存放位置（收纳节点）关联 | 绑定不改变物品业务事实；模型 ≠ 逻辑节点 | 点选模型可查看关联物品与位置 |
| F-04 | 查看与定位 | 在三维场景中浏览、点选模型、跳转到关联物品 | 不以三维为找物唯一路径 | 列表视图同时可达 |
| F-05 | 保存与持久化 | 场景编辑结果保存，本地优先 + 云端同步 | 不做多用户协同编辑 | 刷新/重进后布局不丢失 |
| F-06 | 降级 | WebGL/模型加载失败时切列表管理 | 不阻断物品与库存核心流程 | 列表下仍可完成 F-01/F-03 |
| F-07 | 典型场景初始布置 | 创建房间时除空白房间外，可选典型场景模板（如卧室/客厅/卫生间），按模板预置一组家具模型；预置后为普通家具对象，可继续拖动/旋转/缩放/删除/替换 | 模板是用户主动选择的标准初始布置，不是 AI 自动生成/推荐摆放；不承诺贴合用户真实户型尺寸，不锁定模板家具为只读 | 选模板后房间带一组家具；逐件可编辑且与手动添加一致；模板缺失时降级为空白房间 |

**明确排除**：照片生成三维、AI 家具识别、尺寸自动校准、自动摆放推荐、多人协作、照片级渲染、专业 CAD/BIM 精度。
> F-07 的"典型场景模板"是用户主动选择的标准起点（静态预置布置），不属于被排除的"自动摆放推荐"；模板家具落库后即普通 `furniture` 对象，用户可自由修改，不构成 AI 预测事实。

### 2.2 用户操作流程

**主路径（手动建场景）**
a) 进入空间 → 创建房间 → 填写宽/深/高（或跳过用默认值）→ 选择起点：空白房间，或典型场景模板（卧室/客厅/卫生间等）→ 生成带预置家具的三维房间。
b) 从模型库选择家具添加到场景（模板预置家具可继续编辑/替换/删除）→ 拖动移动、旋转、缩放调整 → 保存。
c) 选中模型 → 绑定物品档案与存放位置（收纳节点）→ 确认。
d) 在场景中点选模型 → 查看关联物品清单与当前位置 → 可跳转物品详情。
e) 随时切换列表视图核对；退出后重进验证布局一致。

**异常/分支路径**

| 场景 | 处理 |
| --- | --- |
| WebGL 不可用 / 模型加载失败 | 自动切列表，创建房间与绑定仍可完成 |
| 模型拖出房间边界 / 缩放超范围 | 钳制到房间边界与合理上下限，给出提示 |
| 删除已绑定物品的模型 | 阻断并提示先解绑或迁移物品（关联保护） |
| 一个物品被绑定到多个模型 | 单物件单位置原则：只允许一个当前绑定，新绑定替换旧绑定 |
| 保存失败 / 离线 | 保留本地编辑与待同步标记，恢复后重试 |

### 2.3 关键数据字段（基于现有模型，标注复用/新增）

| 实体 | 字段 | 类型 | 来源 | 说明与约束 |
| --- | --- | --- | --- | --- |
| rooms | roomId / spaceId / name | String | 复用 | 房间归属与命名 |
| rooms | width / depth / height | Number | 复用 | 房间尺寸，单位米；手动录入，非测量承诺 |
| rooms | layout | JSON | **新增** | 房间布局（墙面/地面/默认视角）；原 photos/task 不再作为主路径 |
| rooms | source | Enum | **新增** | `manual` / `template` / `legacy_photo`，区分手动、典型场景模板与历史照片房间 |
| rooms | templateKey | String | **新增** | 典型场景模板标识（如 `bedroom`/`living`/`bath`）；`source=template` 时必填，空白房间为空 |
| furniture | position{x,y,z} / rotation / size{w,h,d} | Object | 复用 | 三维变换，Y-up、米；缩放体现在 size |
| furniture | modelKey / category | String | 复用 | 模型库标识，缺失时用占位模型 |
| furniture | bindings | Array | **新增** | 绑定关系 `[{itemId, nodeId}]`；或复用 `nodes.furnitureId + items.currentNodeId` |
| nodes | nodeId / parentId / furnitureId / order | String/Int | 复用 | 逻辑收纳节点树；与模型解耦（BR-009），换模型不破坏绑定 |
| items | currentNodeId / locationStatus | String/Enum | 复用 | confirmed/unknown/away/borrowed；绑定写入需与历史同事务 |

> 设计要点：优先复用 `nodes.furnitureId` + `items.currentNodeId` 表达"模型↔位置↔物品"，`furniture.bindings` 仅作为直接绑定的补充，避免两套绑定源不一致。

### 2.4 需要处理的边界情况

| 类别 | 边界 | 处理口径 |
| --- | --- | --- |
| 空间边界 | 模型移出房间、缩放超上下限、角度归一化 | 钳制+提示；统一 Y-up/米 |
| 数据边界 | 空房间/空模型、模型无绑定、物品位置未知 | 显示空态，不虚构位置；允许渐进完善 |
| 模板边界 | 模板缺失/加载失败、模板尺寸与房间宽深高不符、模板家具被改动 | 缺失时降级空白房间；预置家具按房间尺寸钳制到边界内；落库后即普通家具，改动不回写模板（F-07） |
| 关联边界 | 删除含绑定模型、换模型、节点含物品 | 关联保护；换模型保留节点与物品（解耦）；先迁移后删除 |
| 一致性 | 绑定写入、首次位置、重复绑定 | 单物件单位置；首次位置记为"首次确认"非移动；绑定与历史同事务 |
| 交互边界 | 拖拽中断、重复保存、连续点击 | 幂等处理，避免重复记录；失败保留可恢复输入 |
| 环境边界 | 弱网/离线、云不可用、模型库缺失 | 本地优先、待同步标记；占位模型；列表降级 |
| 事实边界 | AI/预测与用户确认 | 本方案无 AI 生成，所有场景结构与绑定均为用户确认事实 |

## 3. 影响分析（SDD 新需求输出）

1. **是否属于当前范围**：部分属于。手动建房间/手动家具本就在 P0（MVP-003/008/009/010），本次是将其从"照片失败后的降级路径"**提升为主路径**；取消照片生成则触及已冻结的 MVP-004/005/007。
2. **需要修改的文档**：
   - `docs/proposal.md`：§5 功能范围（照片上传/尺寸/任务不作为主路径，降级为〔可选〕/〔调整〕）、§6 用户流程（重写主路径）、§8 异常场景、§11 验收标准。
   - `docs/design.md`：§1 技术选型（去掉照片建模路线）、§4 数据流、§5 数据结构（增 layout/source/bindings）、§7 状态流转（移除建模任务状态）、§12 需求-方案对应表。
   - `docs/layouts/`：`示意图-房间照片.md`、`示意图-建模任务.md` 不纳入本轮布局文档范围（未在 layouts 生成；页面仍在代码中注册）；三维房间页（UI-006）需重写为编辑画布。
   - 需求基线：requirement-confirmation.md 重新冻结。
3. **对整体架构的影响**：有——照片私有存储与建模任务链路可下线或转为可选；三维渲染器从"降级项"变为"核心项"，需加强编辑交互（拖拽/旋转/缩放控制）。
4. **新增或调整的任务**：新增"手动布局编辑器""模型变换控制""绑定管理""典型场景模板加载"任务；原照片/建模任务延后或移出 MVP。
5. **对已有功能的影响**：`store.js` 数据结构基本兼容，风险集中在"绑定一致性"与"三维编辑交互"两处，需回归；已通过的 48/48 冒烟断言中涉及照片/任务的用例需复核。
6. **推荐实施顺序**：批准变更 → 更新 proposal → 更新 design → 调整 tasks → 再进入实现与重验。

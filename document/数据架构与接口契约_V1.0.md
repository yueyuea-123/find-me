## 一、架构决策（关键）

### 1.1 数据形态

| 层次 | 职责 |
|---|---|
| 页面层 | 调用同步 `store.xxx()`，零改动 |
| 本地数据层 | `store.js` 基于 `wx.Storage`，全部同步 CRUD，唯一数据源 |
| ~~同步层~~ | **【已移出范围】** `utils/cloud-sync.js` 将在 B2 摘除引用 |
| ~~云函数层~~ | **【已移出范围】** |
| ~~云数据库~~ | **【已移出范围】** |

### 1.2 一致性口径（本地）

- **本地立即生效**：所有写操作落地 `wx.Storage`，用户无等待。
- **关键事务**：`moveItem`（位置+历史）与 `inventoryTx`（余额+交易）在同一函数写入，保证同源。

### 1.3 归属模型（基线 §2）

**归属链：空间 → 家具 → 物品。物品跟随家具，家具跟随空间。**

| 概念 | 口径 |
|---|---|
| 归属空间 `spaceId` | **必填，唯一归属空间** |
| 家具锚点 `anchorType` | 三态互斥：`furniture`（挂家具）/ `space_direct`（空间直挂）/ `unplaced`（未放置兜底） |
| 三维坐标 | 物品**不持有任何坐标**；位置只由所挂家具决定 |
| 房间字段 | 物品**不持有 `roomId`**。挂家具物品的房间归属由家具所在房间推导 |
| 历史 | 归属任何变化都写移动历史 |

> 兼容说明：`space_direct` 与 `unplaced` 都只归属空间，但语义、入口和计数展示不同，不得合并实现。

## 二、本地数据实体设计

所有实体存储于 `wx.Storage` 的 `home3d_store_v1` 键下，结构为 `{ spaces, rooms, furniture, nodes, items, movements, inventory, transactions, alerts }`。

| 实体 | 主键 | 主要字段 |
|---|---|---|
| `spaces` | id | name, archived |
| `rooms` | id | spaceId, name, width, depth, height, calibrated, layout{floor,walls,camera}, source(manual/template/legacy_photo), templateKey, photos[], task{}, archived |
| `furniture` | id | roomId, category, name, model, position{x,y,z}, rotation, size{w,h,d}, source, status, confidence, template |
| `nodes` | id | roomId, furnitureId, parentId, name, type, order |
| `items` | id | spaceId(**必填**), name, category, note, photoPath, trackingMode, currentNodeId, **anchorType(furniture/space_direct/unplaced)**, locationStatus, managementStatus, completed |
| `movements` | id | itemId, type, fromNodeId, fromStatus, toNodeId, toStatus, note |
| `inventory` | id | itemId, balance, unit, threshold |
| `transactions` | id | itemId, type, delta, balanceAfter, note |
| `alerts` | id | itemId, cycleId, status, ignoredAt, recoveredAt |

> **items 实体关键口径（基线 §2）**：
> - `spaceId` 必填，物品唯一归属空间。
> - `anchorType` 三态互斥：有 `currentNodeId` → `furniture`；用户主动不挂家具 → `space_direct`；家具被删除兜底 → `unplaced`。
> - 物品不持有 `position` 等三维坐标，不持有 `roomId`。
> - 房间物品数 = 锚定家具属于该房间的物品数；空间物品数 = 该空间全部物品（按 id 去重）。

### 2.1 V1.2 手动编辑字段约定（CR-001）

| 主题 | 约定 |
|---|---|
| 房间布局 `rooms.layout` | JSON：`floor{w,d}`、`walls[]`、`camera{yaw,pitch,distance}` |
| 房间来源 `rooms.source` | `manual`、`template`、`legacy_photo` |
| 典型场景模板 | 静态预置于 `utils/constants.js` 的 `ROOM_TEMPLATES` |
| 家具变换 | `position/rotation/size`，统一 Y-up、单位米；编辑期越界钳制、角度归一化 |
| 模型—物品绑定 | 单源：`nodes.furnitureId` + `items.currentNodeId`；换外观模型不破坏节点与物品关联 |

## 三、云函数接口清单

> **【已移出范围】** 云端能力已被基线 V1.1 §1、§6 移出交付范围。以下为历史接口设计，仅作归档，不再实现或验收。

统一请求 `{ action, data }`，统一响应 `{ ok: true, data }` / `{ ok: false, error, message }`。

### 3.1 `userLogin` — 登录与身份建立（PRD-001）

| action | 输入 | 输出 |
|---|---|---|
| `login` | {} | `{ openid, isNew, role, status }` |

首次登录在 `users` 建记录；已存在则更新 `lastLoginAt`。登录失败返回明确错误码，不抛异常到前端。

### 3.2 `dataSync` — 全量同步（核心）

| action | 输入 | 输出 |
|---|---|---|
| `pull` | `{ since }` | `{ snapshot: {spaces,rooms,...}, serverTime }` |
| `batch` | `{ ops: [{collection, op, id, data}] }` | `{ results: [...], serverTime }` |

- `pull` 一次拉回该 openid 全部实体（MVP 数据量小，单用户远低于 100 条/集合上限）。
- `batch` 按集合分组顺序执行，同一事务内完成；任一失败整批回滚，返回失败项。
- 每次写入记录 `sys_logs`（level=info，message=集合+操作类型），供后台排障。

### 3.3 `photoService` — 照片私有存储（PRD-031）

| action | 输入 | 输出 |
|---|---|---|
| `signUpload` | `{ roomId, ext }` | `{ cloudPath, fileId }` |
| `signRead` | `{ fileIds[] }` | `{ urls[] }`（短时链接） |
| `remove` | `{ fileIds[] }` | `{ removed }` |

### 3.4 `backupService` — 备份与恢复（PRD-032）

| action | 输入 | 输出 |
|---|---|---|
| `create` | `{ type: 'manual'|'auto', note }` | `{ backupId, recordCount, createdAt }` |
| `list` | `{ page, size }` | `{ total, list }` |
| `restore` | `{ backupId }` | `{ ok, recordCount, restoredAt }` |

- 恢复采用"先建新快照再覆盖"，保证可回滚；恢复过程记入 `sys_logs`。
- 建议备份频率：每日自动一次 + 关键操作前手动一次；保留策略与恢复步骤写入部署文档。

### 3.5 `adminService` — 基础管理后台（PRD-030）

| action | 输入 | 输出 | 权限 |
|---|---|---|---|
| `tasks` | `{ status?, page }` | 任务状态列表（不含照片内容） | admin |
| `logs` | `{ level?, page }` | 错误/警告日志 | admin |
| `users` | `{ page }` | 用户数、状态统计（不含隐私数据） | admin |

- 角色由 `users.role` 决定，管理员 openid 通过云函数环境变量配置（不硬编码）。
- 后台只提供排障所需最小能力，不建设复杂运营平台。

### 3.6 `reportError` — 前端错误上报

| action | 输入 | 输出 |
|---|---|---|
| `report` | `{ message, stack, page }` | `{ ok }` |

写入 `sys_logs`；家庭照片内容永不上报。

## 四、错误码

| 错误码 | 含义 |
|---|---|
| `NOT_LOGIN` | 未取得 openid |
| `PERMISSION_DENIED` | 角色或 openid 不匹配 |
| `INVALID_ACTION` | 不支持的 action |
| `INVALID_DATA` | 字段校验失败 |
| `SYNC_CONFLICT` | 版本冲突（保留两端，记日志） |
| `STORAGE_FAILED` | 云存储读写失败 |
| `BACKUP_NOT_FOUND` | 备份记录不存在 |
| `INTERNAL_ERROR` | 服务端异常（记录日志，前端提示友好文案） |

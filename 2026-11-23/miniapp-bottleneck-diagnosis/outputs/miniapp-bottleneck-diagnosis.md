## 前提

产品方向已确认正确：这是一个**家庭物品管理小程序，核心是物品管理，三维房间是它的呈现层**。因此本报告不把"要不要做这个产品"作为问题，只诊断"方向落地过程中哪一层被拖散"。

---

## 一、结论先行

**不需要整体重立结构，需要"先冻结口径、再做局部收口"。**

判断依据：

- 代码量很小（约 12k 行，其中 3.2k 是第三方 loader），21 页 P0 功能确实存在，数据层 `store.js` 的对外契约也基本稳定。没有到"推倒重写"的程度。
- "哪哪都不对"的主要来源不是工程能力，而是**缺少一个稳定、唯一的落地口径**：范围表、交互规范、README、项目档案、验收报告之间互相矛盾，且在同一天内被多次推翻。实现无论怎么写，都能找到一份文档说它是错的。
- 其次是**三维呈现层与物品业务层的耦合方式错了**：三维页不仅"展示"，还在直接执行业务写、承担口径推导，导致每次交互调整都会牵动物业数据层，返工被放大。
- 工程结构问题（God Page、单体 store、死代码）真实存在，但属于被前两项反复冲刷后的次生问题，且修复成本低，放在口径冻结之后处理。

一句话：**当前瓶颈是"口径治理"，不是"技术重构"；局部结构收口是第二步，不是第一步。**

## 二、现状结构

### 2.1 规模量级（实测）

| 维度 | 实测值 |
|---|---|
| 注册页面 | 21 页（`app.json`） |
| 源码文件 | 108 个 js/wxml/wxss/json |
| 代码量 | 约 12,164 行（含 `package3d/vendor/gltf-loader.js` 3,218 行） |
| 数据层 | `utils/store.js` 1,290 行、约 70 个函数、8 个业务域 |
| 三维页 | `pages/room3d/room3d.js` 978 行、84 个方法、22 个 data 字段、55 处 `store.` 调用 |
| 渲染器 | `package3d/renderer.js` 702 行 |
| 云函数 | 6 个（另有 `quickstartFunctions` 残留） |
| 自定义组件 | 1 个（cloudTipModal）；21 页之间几乎无组件复用 |
| 分包 | `package3d` 1.1 MB（白膜 228K + 带色备份 228K + vendor 676K） |

结论：**绝对规模不大，复杂度集中在两个点**——`room3d` 单页和 `store` 单模块。

### 2.2 模块划分（实际）

```text
pages/* (21 页, 直接 require store)
        │
        ▼
utils/store.js  ── 同步 CRUD（空间/房间/照片/任务/家具/节点/物品/移动/库存/提醒/统计）
        │  commit() 全量写 wx.Storage（home3d_store_v1）
        ▼
utils/cloud-sync.js ── 登录/拉快照/异步推送/墓碑
        │
        ▼
cloudfunctions/{userLogin,dataSync,photoService,backupService,adminService,reportError}
```

三维链路：

```text
pages/room3d/room3d.js
   ├─ wx.loadSubpackage('package3d')
   ├─ require('../../package3d/renderer.js')   ← 分包
   ├─ require('../../utils/store.js')           ← 主包业务层
   ├─ require('../../utils/constants.js')       ← 主包分类表
   └─ 自己实现：触摸拾取/相机/状态机/家具CRUD/房间CRUD/收纳节点查询/物品绑定/缩略图
```

关键事实：**三维页不是"读取物品数据的呈现层"，而是一个并行的业务操作入口**。

### 2.3 三维展示与物品域的耦合点（重点）

这些是"三维是呈现层"这一原则在代码里没有落地的具体位置：

| # | 耦合事实 | 位置 | 影响 |
|---|---|---|---|
| 1 | 页面直接做业务写：移动/旋转/尺寸每点一次就 `store.updateFurniture` | [room3d.js](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/pages/room3d/room3d.js#L445-L530) | 改动三维交互必然改数据层调用 |
| 2 | "待保存/保存/撤销"是 UI 层假象：数据在点击步进时已落盘，`saveScene` 只是重写同值并清 dirty | 同上 + [L533-L558](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/pages/room3d/room3d.js#L533-L558) | 规范 V1.3 §7 的事务语义未成立，容易出"取消没取消掉"类问题 |
| 3 | 离开拦截不可靠：源码注释自认 `onUnload` 拦不到系统返回；"放弃修改"只回滚第一笔 | [L575-L598](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/pages/room3d/room3d.js#L575-L598) | 数据正确性依赖用户走哪条返回路径 |
| 4 | 房间物品口径靠位置反推：`items` 没有 `roomId`，只有 `spaceId` + `currentNodeId`；`listItems({roomId})` 用节点反查 | [store.js L713-L747](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/utils/store.js#L713-L747) | "某房间有哪些物品"是派生值；在外/借出/未绑定物品会消失，口径天然不稳定 |
| 5 | 渲染器反向依赖业务分类表：分包内 `require('../../utils/constants.js')`，按 category/model 映射 GLB | [renderer.js](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/package3d/renderer.js#L458) | 新增/调整家具品类要同时改业务常量和渲染映射 |
| 6 | 缩略图映射写在页面：用中文关键词正则匹配图片 | [room3d.js L19-L43](file:///Users/Admin1/Documents/kywork/3d/iteam/miniprogram/pages/room3d/room3d.js#L19-L43) | 展示细节混入页面，新品类漏图（已出现"只有 3 种家具"类反馈） |

这解释了为什么三维交互的每次调整都会连带产生数据层和测试的连锁修改：**呈现层和数据/业务层之间没有边界，只有调用关系。**

## 三、问题归因

按证据强度排序，不是并列。

### 归因 1（主因）：文档与实现脱节，且存在"多事实源互相打架"

| 证据 | 性质 |
|---|---|
| `V1.2技术口径同步与缺口整改清单_V1.0.docx` 自述：CR-001 只勾了下位文档，"未覆盖 document/ 下 9 份存量文档，形成下位已改、上位未改的倒挂"，逐份标"待改" | 项目自己已承认 |
| `iteam/README.md` 写"全部数据保存在微信本地缓存，不上传任何服务器""无需配置云开发"；`document/小程序项目档案.md` 写 13 集合 + 6 云函数已部署、云同步运行中 | 同一仓库两套互相否定的架构口径 |
| `iteam/README.md` 的三维描述仍是"编辑模式单指拖动/捏合缩放/扭转旋转/长按删除"；`客厅三维空间交互与开发设计规范_V1.3` 明确"默认不直接拖动家具" | README 与当日最新规范冲突 |
| 同一天（2026-11-23）并存 4 份重叠的三维规范（设计基准 V1.0 / 交互逻辑 V1.0 / 客厅交互 V1.3 / 演示交互说明 V1.0），各自自称事实源 | 口径不可判定优先级 |
| `MVP范围冻结清单_V1.1` 仍是 34 项 P0、状态"待签署确认"；CR-001 已把 MVP-004/005/007 降为可选，冻结清单未同步 | 范围基线失效 |
| 高保真交付稿只有 8 页，小程序注册 21 页；提交 `3faee6a` 却一次性把 21 个 wxss 全部换色 | 13 页没有设计基准，却被"对齐"了 |
| 验收报告与项目档案反复出现"全部通过""零回退"，但同一天仍有 5 个真机修复提交 | 文档结论领先于事实 |

**影响**：任何一次开发都能被另一份文档判为"不对"；每轮交付都在重写口径。这是"哪哪都不对"的直接来源。

### 归因 2（强）：范围切分与交互口径反复，且改动集中在呈现层

- 40 个提交全部集中在 6 天内，2026-11-23 单日 11 个。
- 按提交主题粗分：三维/白膜/渲染 ≈ 11 次，视觉/demo/原型 ≈ 15 次，fix ≈ 10 次，纯物品/库存 ≈ 4 次。
- 2026-11-23 三维页同一天连续返工链：`d030b61`（固化交互）→ `7209ec5`（真机无家具）→ `14725df`（拖动/旋转/缩放方向）→ `aa14364`（同步重复房间/编辑丢失/拖动）→ `3faee6a`（视觉与功能大改）→ 工作区仍有未提交改动。
- 交互方案在同一天被推翻：V1.0/V1.1 的"拖动摆放"→ V1.2/CR-001"手动自由编辑"→ V1.3"禁止拖动、按钮步进"。
- 物品视图口径同一天从 `spaceId` 改为 `roomId`（项目档案 §八·补3/补4），并在文档里自我记录为"产品口径变更"。

对照已确认的产品定位：**核心是物品管理，三维是呈现**。但实际投入分布明显向三维呈现倾斜，且每次倾斜都回到物品数据层改口径。这是"落地过程中被拖散"的主要形态。

**推测（需用户确认）**：用户"哪哪都不对"的体感，很可能来自三维页在真机上的连续不稳定（无家具、方向不对、返回后消失、物品归属不对），而不是物品管理主流程本身不可用。

### 归因 3（中，已现临界征兆）：工程结构

| 问题 | 事实 |
|---|---|
| God Page | `room3d.js` 978 行 / 84 方法 / 22 状态字段，同时管 GL 生命周期、状态机、家具/房间 CRUD、收纳查询、物品绑定、缩略图 |
| 单体数据层 | `store.js` 1,290 行 / 8 域；整库一个 JSON，每次写全量落盘；无 schema 校验层 |
| 无组件化 | 21 页只用 1 个通用组件，列表/卡片/空态/表单在各页重复实现 |
| 死代码 | `utils/webgl-renderer.js`(193) + `utils/room-renderer.js`(228) + `utils/mat4.js`(101) 无页面引用 |
| 冗余资产 | `package3d/assets/furniture_colored_backup/` 228K 随包发布 |
| 门禁语义 | `qa/check_and_score.py` 是结构分（配置/四件套/JSON/路由/资源/字段存在），`smoke-test.js` 是 mock 运行时调用页面方法；都不能证明真机渲染与手势正确。项目档案中 `quality-report.json` 被提交 11 次 |

**注意**：结构问题目前是"可维护性变差 + 返工放大"，还没有到"无法继续开发"。把它排在口径之后处理是合理的。

### 归因 4（弱，不作为主因）：数据模型

物品模型本身（spaceId/currentNodeId/homeNodeId/locationStatus/managementStatus/trackingMode）与业务规则是自洽的；问题在于**"物品属于哪个房间"没有成为显式事实字段**，只能从位置反推。这在"三维按房间展示物品"的需求下会持续产生歧义。属于"呈现需求倒逼数据模型"的一个未闭合点，但不建议现在大改模型。

**推测**：如果后续三维要继续按房间/按家具聚合物品，显式增加 `roomId` 或"归属位置"字段会比继续用节点反推更稳；但这需要产品先确认口径，不能由开发臆定。

## 四、是否需要重新梳理

**需要梳理，但不是"重新立结构"，而是"冻结口径 + 局部收口"。**

区分两种做法：

| 做法 | 判断 |
|---|---|
| 整体重立（换框架、重写页面、重做数据模型） | **不建议**。代码量小、功能在、契约稳；重写只会把已有的 34 项 P0 和 15 个 BR 规则再踩一遍 |
| 局部收口（先冻结唯一口径，再拆三维页边界，再清结构债） | **建议**。成本低、可验证、直接打断"改一次崩一次"的循环 |

"重新梳理"的对象应该是**文档与口径**，不是代码目录。

## 五、最小必要动作清单（按优先级）

### P0：先做，做完再谈其他

1. **建立唯一事实源（半天级）**
   在 `document/` 放一张《当前基线一页纸》，只回答 5 个问题：
   - 是否包含云同步？（README 与项目档案必须二选一）
   - 三维交互以 V1.3 为准，V1.0/V1.1 的拖动口径作废，README 同步改
   - MVP 范围以哪版为准（34 项 P0 是否含 MVP-004/005/007）
   - 21 页中哪 8 页有设计基准，其余 13 页按什么标准验收
   - demo / prototype / miniprogram 三套产物的定位（讲解 / 归档 / 交付）
   所有其他文档头部加"若与本文冲突，以本文为准"。

2. **做一次真机一次性走查，停止同日连续重构（1 天）**
   把"改代码 → mock 全绿 → 真机又不对"的循环打断。只记录问题清单（页面、操作、现象、机型），只修阻断主流程的问题，不在走查期间改交互方案。

3. **划清三维呈现层边界（1–2 天，纯结构调整，不改行为）**
   把 `room3d.js` 拆成 4 块，页面只做编排：
   - 渲染适配层（GL 生命周期、分包加载、触摸坐标）
   - 场景状态机（VIEW/SELECTED/MOVE/ROTATE/DIMENSION/保存/撤销）
   - 物品/家具只读查询（房间物品、节点计数、缩略图）
   - 页面交互（事件绑定、跳转）
   目标是把 84 个方法降到页面层 20 个以内，业务写仍走 `store`。

4. **修正"待保存"语义（与第 3 项同批）**
   V1.3 要么改成"即时生效 + 撤销"，要么真的改成草稿态（不落盘、确认后一次提交）。二选一，写进基线，不能让 UI 文案和数据结构继续各说各话。

### P1：P0 稳定后再做

5. **文档-实现对账表**：21 页 × 设计稿 / 交互说明 / 实现 三列，标"有/无/冲突"，只补冲突页，不重写全部文档。
6. **清理结构债**：删 3 个无引用模块（约 522 行）、移除 `furniture_colored_backup`、把重复的列表/空态样式抽成 2–3 个组件。
7. **QA 语义校准**：明确 `100/100` 只代表结构合格；把真机验收清单单独成表，报告里不再用"全绿"覆盖真机项。
8. **数据模型评估（仅评估，不实施）**：是否需要给物品增加显式房间归属；由产品确认后再动。

### 现在明确不该做的

- **不要整体重写、换框架（Taro/uni-app）或重做数据模型**。收益低、风险高，且解决不了口径问题。
- **不要继续在同一天推翻交互方案**（拖动 ↔ 按钮、空间口径 ↔ 房间口径）。
- **不要为了过门禁去改测试断言**。历史提交里已多次"按新口径更新断言并注明原因"，这会让门禁失去回归价值。
- **不要扩展 P1/P2 能力**（AI 识别、照片建模、反向定位、订阅消息等）。核心物品管理还没在真机稳定前，扩功能只会加重"哪哪都不对"。
- **不要继续对 13 个无设计基准的页面做视觉重构**。先定验收标准。
- **不要在口径未冻结前拆分 `store.js`**。字段口径还在变，此时拆模块会把错误固化。

## 六、不确定与推测声明

以下内容未被仓库直接证实，标注为推测：

1. **用户"哪哪都不对"的具体触发点**：推测集中在三维页真机表现（据 2026-11-23 的连续修复记录与文档中的用户反馈转述），但未获得用户本人的复现描述。
2. **云同步是否仍在交付范围**：README 与项目档案矛盾，无法从代码判定哪个是当前意图；需产品决策。
3. **13 个无设计基准页面的实际视觉质量**：仅从代码与文档判断，未做真机目视。
4. **物品房间归属是否必须显式化**：属于对后续需求的推断，当前需求下用节点反推也能工作，只是口径不稳。
5. **真机性能/帧率/机型兼容**：无真机日志，文档中的"通过"仅指模拟器自动化。
